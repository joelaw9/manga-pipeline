# manga_pipeline spec — Metadata

Part of the spec; the index is [`SPEC.md`](../../SPEC.md). Update this file in the same change as the behaviour it describes.

## Metadata

Everything `ComicInfo.xml` can hold is written there, except `Count`: a completed series' publication status is set through the Kavita API and locked, so its chapters are not all rewritten when 1 more arrives. What Kavita needs beyond the file is written through the Kavita API; for a new series, once Kavita has indexed it. A CBZ that arrives without a `ComicInfo.xml` gets one.

### Series fields

A series' fields come from its stored records alone:

| Field | From |
|---|---|
| summary | the first of AniList, MangaDex (English), MangaBaka, MangaUpdates that has one, as plain text (HTML and Markdown read by their parsers; a MangaDex summary ends at its first horizontal rule; a closing "(Source: …)" note dropped) |
| genres, tags | SPEC "Tag rules" |
| publication status | MangaBaka: releasing or upcoming = Ongoing, hiatus = Hiatus, completed = Completed, cancelled = Cancelled; never Ended |
| age rating | MangaBaka's content rating: safe = Everyone, suggestive = Teen, erotica = Mature 17+, pornographic = Adults Only 18+ |
| language | MangaDex's original language |
| writers, pencillers | AniList's staff in the role Story or Art, and Story & Art for both |
| web links | 1 page per source whose record was found, and MyAnimeList |
| provider ids | AniList, MyAnimeList and MangaBaka ids (SPEC "Source ids"); AniList 0 when the series' AniList id has no record (a novel's, or gone), which clears the id Kavita holds |

`export` writes a series' fields to Kavita, each locked, when the data version, the tag rules or the code that makes and writes them changed since its last write, its cover changed, or Kavita holds the series under a new id; it writes only the fields Kavita does not already hold. It writes nothing while a library scan is awaited (SPEC "Publishing"): Kavita holds such writes back. A field with no value at the sources is left as it is. Web links are added (1 per source), and a link to a source's page for another id than the one written for that source is removed (every AniList link when the AniList id is 0), each removal logged. Writers and pencillers are only added: Kavita keeps the people its scans read from the files whatever an update sends. Lists are compared under Kavita's name normalising. Each field is recorded as soon as Kavita accepts it. The cover is uploaded when Kavita does not hold the series' current cover from the pipeline, and Kavita must then serve it; a cover uploaded to Kavita before the pipeline's first upload, and not by the old tool, is a person's, kept and reported once (Kavita names every upload alike, so a person's upload after the pipeline's is not told apart). A series Kavita no longer holds is not written, and is not tried again until one of the reasons above holds anew.

A locked Kavita field that is overwritten, not only added to (above), is overwritten only when it holds the value the pipeline last wrote there, or, for a field the pipeline has never written to the series, a value the old metadata tool wrote (its summary, genres and tags as its state file lists them, and the publication status of every series its state file lists a written field for, or the status its state file names). Any other locked value is a person's edit: it is kept, and reported once in the log. A list write removes the entries the sources no longer give. It only runs from a completed check, which reached every source: a source that fails (unreachable, an error, a reply of an unexpected shape) ends the check storing nothing, and a source with no record is stored as not found, which is definitive: its title search accepted no hit, its stored id answered 404 (the entry is gone or merged), or its record is a novel's.

### ComicInfo

The comicinfo stage writes every new chapter's `ComicInfo.xml`, valid for the ComicInfo v2.1 schema:

| Element | From |
|---|---|
| `Series`, `LocalizedSeries`, `Title`, `Number`, `Volume` | SPEC "Publishing" |
| `Summary`, `Genre`, `Tags`, `LanguageISO`, `AgeRating`, `Writer`, `Penciller` | the series' fields (above); lists joined with ", "; left out when the stored records give none, never taken from the download, but `Genre` and `Tags` of a series whose records give neither: the file's own, as it has them (the download's, or the published file's on a rewrite or a join) |
| `Web` | the series' web links, then the chapter's page at its Suwayomi source (Suwayomi's `realUrl`), separated by spaces |
| `Notes` | `Source: <source>` (the Suwayomi source's display name, as the chapter records it) |
| `Manga` | `Yes` for a strip series (SPEC "Conversion", layout). A page series by its MangaBaka type: `manga` is `YesAndRightToLeft`, any other type is `Yes`. A page series MangaBaka has no record or no type for: `YesAndRightToLeft` when its original language (MangaDex) is Japanese, `Yes` when it is another; with neither, `Yes` when its stored genres or tags hold Manhwa, Manhua, Korean, Chinese, Webtoon, Long Strip or Web Comic, else `YesAndRightToLeft`. A file's own genres never count |
| `SeriesGroup` | the series' override file's `series_group` (a name, or a list of names joined with ", "; a name holds no comma), left out without one |
| `Translator`, `ScanInformation`, `Year`, `Month`, `Day`, and any other element valid for the schema | the download's own `ComicInfo.xml` |
| `PageCount`, `Pages` | the staged CBZ's pages as convert wrote them: per page its index, width, height and bytes, `FrontCover` on an inserted volume cover, and `DoublePage` on a page wider than tall in a page series |
| `BlackAndWhite` | `Yes` when convert found every page gray, else `No` |

The source and its page are those of the download the chapter goes out with: a re-download's (SPEC "Bad downloads") replace the first download's. A hand-placed chapter has no source: no chapter page in `Web`, no `Notes`. A chapter whose series has never completed a metadata check waits on `metadata_check` at validate, at no attempt; `intake` ends the wait once the series' first check has completed, whatever it found (a series on a platform volume basis also waits for a check its new chapter made due: Platform lists).

## Source ids

A series' metadata comes from 4 sources: AniList, MangaUpdates, MangaDex and MangaBaka; MyAnimeList ids are kept too (Kavita's `malId`), though MyAnimeList is never fetched. Each id a series holds is stored with its origin:

| Origin | Ids |
|---|---|
| `suwayomi` | a linked Suwayomi manga's tracker records (AniList, MangaUpdates) and the MangaDex id in its URL |
| `kavita` | the series' Kavita web links and its `aniListId`, `malId`, `mangaBakaId` |
| `anilist` | the MyAnimeList id of the fetched AniList record |
| `mangabaka` | the cross-links of the fetched MangaBaka record (AniList, MangaUpdates, MyAnimeList) |
| `mangadex` | the cross-links of the fetched MangaDex record (AniList, MangaUpdates, MyAnimeList) |
| `search` | found by a title search, or the 1 id links in the linked Suwayomi manga's descriptions give |
| `import` | the old metadata tool's state file (SPEC "Metadata checks", import) |
| `human` | `series set-id SERIES SOURCE ID` |

Ids are compared in 1 form per source: a MangaUpdates id as the number its base-36 text spells (an all-digit MangaUpdates link is a retired legacy id and is ignored), a MangaDex id as its UUID. Every id a series holds for 1 source must be the same, whatever its origin; when 2 differ, the series is `needs_human`, naming the source and each id with its origin, and its check stops there. A `human` id wins: for that source no other origin is compared. `series set-id` stores it (refused with exit 2 for a series that does not exist, a source not in the list above, or an id that is not that source's form), removes every id of origin `search` the series holds and makes its check due at once, so that check searches them again; `retry --series` then clears `needs_human`. 2 series holding the same id is not a disagreement: each series is judged alone, and Series identification treats that id as a double hit, as does a new series' admission (SPEC "Series identification").

A source no origin gives the series an id for takes, before the sources are searched, the id its linked Suwayomi manga's descriptions give: an AniList, MangaUpdates or MangaDex series page linked there, with or without `https://`, when the descriptions give exactly 1 id for that source and that id's record is neither a novel's nor gone. A source still without an id is searched by the series' names: its Kavita name, alternative, localized and original names and its `ComicInfo.xml` `Series`, or, for a series Kavita does not hold, the names it was found by (the Suwayomi title; a hand-placed folder's title folder name and `ComicInfo.xml` `Series`); then each of those names with up to 2 trailing bracketed suffixes removed, 1 at a time ("Title (Official)" and "Title 〘Official〙" also search as "Title"). Names equal under the lenient key are searched once. AniList and MangaDex are searched by the series' names, then MangaBaka's main title (MangaUpdates' when the check found no MangaBaka record), then the suffix-stripped names, then MangaBaka's (else MangaUpdates') other titles. At most the first 4 names are searched (8 for MangaDex); a result is accepted against every name of the list. In this order: MangaBaka through its AniList or MangaUpdates id, and by a title search only when the series holds neither or they lead to a novel; MangaUpdates by title; MangaDex by its MangaUpdates link; AniList by title. A search hit is accepted only when exactly 1 result's title or alternative title equals a name under the lenient key (SPEC "Series identification"); for MangaBaka, also its top result for the first name when that result is close to a name (`rapidfuzz` ratio of the lenient keys at least 90, or 1 key of at least 15 characters starting the other) and no other result is; for MangaUpdates, also exactly 1 of its top 3 results whose associated names hold a name. A name ending in `(Manhwa)`, `(Manhua)`, `(Manga)` or `(Webtoon)` (or the same in square brackets) limits MangaUpdates results, and MangaBaka's title search results, to that type; Webtoon means Manhwa or Manhua. A novel never matches, and a record a check fetches by an id that turns out to be a novel's is not used and is logged: that source has no record until a person fixes the id (`series set-id`). An accepted id has origin `search`. A source whose search finds nothing is recorded as such for the check; every later check searches again.

## Tag rules

The tag rules (consolidation, derived tags, promoted tags, allowlist, top-up exclusions, top-up last names) are files of the program, written by hand. A change to them reaches every series: the sync records hold a fingerprint of the rule files, and when it changes, each series' tags are worked out again from the stored source data, with no source lookups. Series whose tags change are rewritten (SPEC "Retroactive updates").

The rule files are part of the program (`manga_pipeline/metadata/tag_rules/`, so the fleet's version covers them): `consolidation.csv` (a name of a kind becomes another name or kind, or is removed), `derived_tags.yaml` (a tag or genre given when a series' terms match a rule), `promote_tags.txt` (a tag given whenever the series' rule terms (step 3) hold it, at a minimum MangaBaka weight when 1 is named; a term from another source, or from MangaBaka's genres, status or type, counts at any weight, unless it is spelt exactly as a MangaBaka tag: MangaBaka carries MangaUpdates' categories and weights the low-vote ones incidental, so a category it repeats keeps MangaBaka's weight), `tag_allowlist.txt` (tags a top-up may add: hand-picked names, and the story tags kavita_enrich's library held when the pipeline replaced it, copied once into the file), `top_up_exclude.txt` (names a top-up never adds) and `top_up_last.txt` (generic tags a top-up may add, which it takes only after every other candidate: Female Protagonist, Male Protagonist; a name in it may not also be in `tag_allowlist.txt`). The fingerprint is the sha256 of the 6 files and of the code that applies them (the tag module and its name key), so a change to either recomputes every series. A rule file that cannot be read as its kind (an unknown kind or weight, a rule without terms) stops the run, naming the file and the entry. A name reaches a series in 1 spelling: a consolidation row converts every spelling of its name (case and punctuation aside) to its target, and a name that sources spell differently and that reaches a series' lists has a row to the spelling most source records use.

A series' genres and tags are worked out from its stored records, in this order:

1. The sources' lists. Genres come from MangaBaka (its genres, and its tags marked as genres that no other tag implies, at a weight other than incidental; of those tags, Smut, Adult and Hentai count only when its content rating is erotica or pornographic) (or from MangaUpdates when MangaBaka does not know the series), AniList, and MangaDex's genre tags. Tags come from AniList (rank at least 60, not a spoiler) and MangaDex's theme tags; a tag equal to a genre is dropped.
2. Consolidation. Every name goes through the table, under its own kind, else the other. A MangaUpdates plural marker (`Angel/s`, `Elf/ves`), a final `s` after 4 letters, case and punctuation do not tell names apart; a tag equal to a genre is dropped, here and after step 3.
3. Derived and promoted tags. Rules match the series' terms:
   - MangaBaka's genres, tags, status, content rating and type;
   - MangaUpdates' categories and genres, too, when MangaBaka has fewer than 10 tags;
   - MangaUpdates' terms and type alone, when MangaBaka does not know the series.
4. The top-up, which brings a series to 4 genres and 6 tags. It draws from MangaBaka's genres and its tags of core, defining, recurrent or no weight, and adds only names that are a consolidation target or in the allowlist and not excluded. Names in `top_up_last.txt` come after every other candidate, whatever their weight. A series still short tries again with the MangaUpdates categories MangaBaka lacks. Past the minimum, only allowlisted tags and tags the table makes genres are added, and only at a core, defining or recurrent weight.

A top-up never adds a name because other series of the library use it, so a series' lists never depend on the order series are written.

A fix a person makes while answering a `needs_human` item, such as a series' source ID, is stored in the database.

## Metadata checks

How often a series is checked against its sources depends on how long ago its last published update was, not on its status alone. A series marked complete still receives epilogues, side stories and tag changes, so no series is ever exempt.

| Last published update | Checked |
|---|---|
| less than 6 months ago | weekly |
| 6 months ago or more | monthly |
| 12 months ago or more, and marked complete | yearly |

A new chapter arriving for a series makes its check due at once. The periods and intervals are settings (`metadata.*`, SPEC "Config"). The last published update is the newest chapter upload date Suwayomi holds for a manga linked to the series; for a series with no linked manga, the publish date of its newest MangaDex chapter; with neither, the series is checked monthly, marked complete or not. A series is marked complete when a linked manga's Suwayomi status is completed, or its MangaBaka status is. Kavita's dates and a hand-placed file's time never count.

Every series of `kavita.library_id` in scope (`series.only`) is checked, and every new series Kavita does not hold yet (SPEC "Series identification"): its check has no Kavita record, and searches by the names it arrived under and, once admitted, its name. `intake` lists the library each run and stores each series it does not hold, with its names, and takes the current names of each series it holds; the folder of a Kavita series is fetched when first needed (its first download, or the daily baseline pass). The daily baseline pass runs after the run's due checks; it takes the baseline of every in-scope `ok` series Kavita holds that has none (SPEC "State"): from its record, or adopting those whose folder holds no record and whose metadata check has completed; a series Kavita gives no single folder is, when it could be adopted (no baseline, a completed check, no chapter at discover), adopted all the same, which holds it; else it is left as it is. A listed series is matched to a row by its Kavita id, else to an admitted new series Kavita did not list before (SPEC "Publishing": by its ComicInfo name and its folder; a listed series of that name in another folder gets no row while the new series is unmatched), else, for a row whose Kavita id is no longer listed, by its names (its ComicInfo `Series` name among them), confirmed by its folder (a row with no folder yet: by its names alone, when exactly 1 such row matches) (Kavita recreated the series under a new id: the row takes the new id, and this is reported in the log); else it is a new row. A series' folder that cannot be found does not stop its check; a series Kavita no longer holds is not checked, and its next check moves by the quiet interval; once Kavita recreates it, it is checked at the next `intake`.

`intake` runs the checks before its chapter work, and a series' due check before its new chapters are validated. Kavita or Suwayomi unreachable while the library is listed skips the checks for the run; the chapter work goes on. A check made due by a new chapter, a series' first check and a new series' first check always run; of the others at most `metadata.checks_per_run` run, the longest due first. A check:

1. gathers the series' ids from its linked Suwayomi manga and its Kavita record (SPEC "Source ids");
2. fetches MangaBaka (by id, else found as Source ids says), then the other sources' records by id, searching for those with none: MangaUpdates' series record, MangaDex's series record, volume aggregate and cover list (and, once they are fetched, its English chapter list: [chapter number, title] in upload order, stored outside the data hash, as a platform list is, since a new chapter is not a data change; a check with no MangaDex record removes it), AniList's media record with its staff; the cross-links of each record add ids, and every id is compared (SPEC "Source ids") before it is used; a source with no id at its turn is fetched once the others are, when a later record's cross-links give it one (by that id, with no search);
3. stores each fetched record with its hash (a character the database cannot hold, a NUL or a lone surrogate, removed from its text), and "not found" for a source with no id after its search;
4. picks the series cover (below) and fetches it;
5. completes: the series' data version rises by 1 when any stored hash changed (a record's hash leaves out the fields that change with the source's own activity and that nothing reads: its counts, ranks, ratings, vote totals and update times), and on its first completed check whatever it found; the next check is set by the table above. A check whose series' stored ids changed while it ran (`series set-id`) stores nothing and stays due.

A service that cannot be reached, or answers with an error or a reply of an unexpected shape, ends the check storing nothing: it stays due for the next run, and it never holds the series' chapters or stops the run (a failing share does). Each check is 1 log line: the series, the sources fetched, found or not, and whether the data changed.

When a completed series' check is due, its Suwayomi chapter list is refreshed (SPEC "Suwayomi").

### Covers

A series' cover is the Suwayomi thumbnail of a linked manga when it is at least 1500 px wide; else a MangaDex cover, the first of: English volume 1, the lowest-numbered English volume, volume 1 in the series' original language, volume 1 in any language, the series' main cover; else the wider of the AniList cover and the Suwayomi thumbnail. A series with no linked manga skips the Suwayomi steps; with no source either, it has no cover. An image that cannot be read (an error page served as the image), or one its host no longer has, is skipped as if the source had none. The chosen image is stored as `series/<sha256>.<ext>` under `paths.covers` and recorded with its source URL; a file there no series names is deleted once it is a day old.

### Volume covers

A main volume from MangaDex or an override file, or a file-name volume that an agreeing override file or MangaDex gives the same, is covered. The first chapter of a covered volume (the lowest-numbered main chapter of it, published or open) takes the volume's cover as its first page when it is new: at validate, `intake` takes MangaDex's cover of exactly that volume (English, else the original language, else any), stores it once per series and volume under `<paths.covers>/volume/` (fetched again when its file is missing or holds other bytes), and hands it to convert. MangaDex with no cover of that volume, or no longer serving its file: the chapter goes on without one. A fetch that fails, or that returns something other than an image, fails validate's attempt. A volume another open chapter of the series already took the cover of, or a published file holds or is queued to hold (below), is not covered again. A chapter that has its cover keeps it; a lower-numbered chapter of that volume that arrives later takes none. A published file's cover is kept right by retroactive updates (below). A cover file no series volume or chapter names is deleted once a day old.

### Platform lists

A series published on an official platform (Tapas, Webtoons) has that platform's episode list, fetched at each of its checks: the platform its Kavita links name, else (none named there) its AniList record's English Tapas or WEBTOON streaming link; a series whose recorded volume basis is a platform's uses that platform only, any other tries Tapas first, then Webtoons when Tapas has no list for it. A Webtoons link under `/canvas/` or `/challenge/` is a Canvas series. The list is the site's posts in order, each a main chapter, a special or a notice, with its number, cleaned title and season marker (the bulk converter's reading), the season ranges those markers give, and its coverage (partial when the site lists fewer than it counts, numbers are missing, nothing is listed, or Webtoons keeps episodes to its app). A page that is gone (404, 400, an unknown Webtoons number, a Tapas page with no series id) is no list, and the stored list is removed; so it is when no link names a platform. A list is not part of the series' data: a new episode does not change it. Tapas answering 403 (blocking) is unreachable for the run; any other error ends the check as for every source. While a series on a platform volume basis has a check made due at once by a new chapter that has not completed, its chapters wait at validate (`metadata_check`), so its chapters are never named from a list older than their arrival. A new list replaces the stored one unless it is of the same page and lists fewer main chapters; a page gone after its first part is an error, not "no list".

### Import

`metadata import STATE_FILE CONFIG_FILE` reads the old metadata tool's state file (`.sync_state.json`) and its config's `map` and `overrides`. It first brings the series rows in step with the library, as `intake` does, and imports only series that exist in the library and are in scope, reporting the rest. From the state file: each id, with origin `import` (a `null` id, "searched, nothing found", is skipped: every check searches again); each cover's hash, as the cover Kavita already holds; and which Kavita fields the old tool wrote and the publication status it set (SPEC "Retroactive updates" reads them). Every genre and tag list Kavita holds locked at the import, for every in-scope series Kavita lists, the state file's or not, counts as the old tool's: the old tool locked every list it wrote, and the state file does not list them all. The import runs before the first `export`; once `export` has recorded any series' write (`series_written` holds a row), `metadata import` refuses (exit 2) and imports nothing, so a lock set after the cutover is never taken for the old tool's. A series Kavita recreates under a new id loses what the import recorded for it. `map` (a JSON file, its path relative to the config's folder) and `overrides` (both Kavita series name to Suwayomi manga id or title) become links of those manga to those series. It can run again until the first `export`: it replaces the ids it imported before, and never touches another origin's. An imported series holds no fetched data, so its first check is due.

### Audit

`metadata audit` is read-only, opens no database and ignores `series.only`. For every series of the library it gathers each origin's ids itself (Kavita, Suwayomi trackers of the manga matched to it, the state file given by `--state PATH`, and MangaBaka's and MangaDex's cross-links, fetched at their rate limits), and lists the series whose ids disagree, per source the series no origin gives an id for, and the Suwayomi library manga no series matches by name.

## Retroactive updates

A check can change what already-published chapters and series should carry. Series-level fields (summary, genres, tags, status, age rating, people, language, links) are rewritten through the Kavita API, where they are locked (SPEC "Metadata").

A published chapter's file is rewritten when its volume, its volume cover or (by a hand edit) its title should change, and only then. A published main chapter's volume changes from none to a volume (its series' gap fill, or its volume basis newly giving one), or to the volume its series' override file gives its number (a range or a volume start applies only to a chapter that carries no season). A source moving a published chapter to another volume, or dropping its volume, changes nothing; `naming diff` lists it. Its number and kind are never changed, and its title only by a hand edit (below), or, for an untitled file, by a better copy (below). A pipeline-published file whose name holds another volume or title is renamed (SPEC "Publishing": `Vol.{V} Ch.{N} - <title>`); a bulk-converted file keeps its name until a better copy replaces it (below).

Each published file records the volume cover it holds: none, the cover of volume V, or none because a cover image could not be inserted (`unfit`, with that image's sha256). Publish records it for a pipeline file (the volume of the cover convert inserted); a bulk-converted file's comes from its series' bulk record (the file its `covers.volumes` names for each volume), and a pipeline file published before this was recorded is read once from its member list (a page `000_cover` is the cover of its volume); an adopted file's is read from its member list the same way, at adoption. The comparison fills the unknown ones of a series before comparing it; a record or file that cannot be read leaves them unknown, is logged, and the series is not compared in that run (`status` counts the series with unknown covers).

A covered volume (SPEC "Volume covers", over the volumes the published files will hold) whose published files hold none of its cover, and whose cover no open chapter took, gets it in its lowest-numbered published main file. A file holding the cover of a volume other than its own drops it, unless it is that lowest file (its cover is then replaced). Every other file keeps what it holds, a second holder of 1 volume included. A cover that could not be inserted into a file is not tried again until the volume's cover image changes. The cover image is the one SPEC "Volume covers" picks; when the series' stored MangaDex cover list has that volume and no image is stored yet, the comparison records it as wanted and leaves that file's cover for later (its volume still changes), and the next `intake` fetches it (at most `workflow.attempt_limit` fetches whose answer is wrong, then `status` lists it; MangaDex unreachable, timing out or failing on its side spends no attempt and stops nothing else); the stored image changes the series' naming inputs, so the next `export` compares it again. Each check of a series, once its MangaDex cover list is stored, fetches again every stored volume image whose volume MangaDex now chooses another file for (SPEC "Volume covers": English, else the original language, else any); so does any use of the image (validate, a wanted fetch). A different image replaces the stored one, and the published files holding the old one are marked as holding a stale cover of that volume (a chapter published from the old image too): a stale file of that volume takes the new image in place of the old, any other stale file drops it; a new image unfit for a file leaves it without a cover. A stored file still among MangaDex's best-ranked covers of the volume is kept (MangaDex lists a volume's covers in no fixed order). MangaDex choosing no file, or no longer serving the chosen one, leaves the stored image, and the next check asks for that file again; MangaDex unreachable, timing out or failing on its side leaves the series' check due again. `series refetch-covers SERIES_ID` makes the series' check due at once.

`export` compares, at the start of each run, every in-scope series that is `ok`, has a Kavita id and has its baseline taken, when its naming inputs changed since it was last compared (a hash of its volume basis, its override file, its stored MangaDex aggregate, cover list and platform list, its stored volume cover images, the naming code, its published files' rows, its open downloads and the volume covers they took, and its open rewrites). It compares confirmed published files with no open chapter and no rewrite pending; an adopted file (origin `library`, SPEC "State") is never compared: it keeps its name, volume and cover until it is converted, takes no volume cover, and counts for covers and naming at the volume it holds; a file it skipped changes the hash when its chapter ends, so the next run compares it. At most `export.rewrites_open` rewrites are open at a time (not counting `needs_human` ones, nor chapters that replace an adopted file, nor rebuilds, which have their own count: SPEC "State"); at 0 no rewrite is queued and export compares nothing; a series left unfinished is compared again by the next run. A series whose override file cannot be read is `needs_human`, as at the comicinfo stage.

A rewrite never re-encodes pages. It is a chapter of kind `rewrite` that carries every change of its file (volume, name and cover) and goes through convert (when its cover changes), comicinfo and publish:
- convert (`process`) copies the library file's members in order byte for byte to staging, leaving out any cover page it holds (`000_cover`, whatever its record says), and puts a new cover in first, encoded as a new chapter's is (SPEC "Parts", convert: scaled to the most common width of the other pages, in the format they share; AVIF only when it scores at least 80). Pages of more than 1 format, or an AVIF cover under 80: the cover cannot be inserted; a file holding another volume's cover still drops it, one holding none whose volume does not change is left as it is (the chapter is dropped), and the file records the image as unfit. A copied member whose CRC differs from the source's, or a cover that does not decode in its format, fails the stage.
- comicinfo copies the library file to staging with its `ComicInfo.xml` replaced and every other member copied byte for byte (checked against the source's member list and CRCs); after convert it replaces the `ComicInfo.xml` of convert's staged file, with the old file's `Page` entries shifted: an inserted cover adds a `FrontCover` entry at its place in reading order (its size and bytes) and 1 to every index from there, a dropped cover's entry is removed and those after it take 1 off; `PageCount` is the new page count. An old file with no `Page` entries gets none. The new `ComicInfo.xml` carries the current series-level fields, the new volume, and every other field of the old file (its own: number, title, translator, scan information, date, black-and-white, notes, page count, pages, and whatever else its download carried); `Web` holds the series' current links, then the old file's other links.
- publish takes a snapshot of the API key's user's reading progress on the file and queues the rewrite on the file's published-file row (the target name, the staged file, the new values and cover, the progress and the page count's change); it refuses (`needs_human`) a target that exists, on disk or as another published file, and is not the file being replaced. The chapter is then done; the row carries the rest.
- every `export`, after its publishes, finishes each queued rewrite (this run's, and any a crash or a reset left), 1 try a run, recording each step on the row so a retry starts at the next one: the staged file's modified time is set to now; the old file is hard-linked into `<paths.retention>/library-files/<its folder below the library root>/` (a free `(n)` name) and given the retention period; the staged file is renamed over the target; a renamed file's old name is removed; the row takes the new path, size, volume and cover. The library never lacks the chapter's file. A step that fails records its error and 1 attempt on the row and is tried again by the next run from that step; the other rows and the run go on. At `workflow.attempt_limit` attempts the row waits for a person, and `status` lists it: `rewrite retry FILE_ID` tries it again from its next step; before its file is renamed in, `rewrite drop FILE_ID` gives it up instead (its staged file removed; the next comparison starts again). A row whose staged file is gone before it is renamed in is given up the same way, logged. A rewrite chapter held `needs_human` (a target taken) is given up by `chapter drop`. `state reset` keeps the staged files of queued rewrites.
- once Kavita lists the new path at its size, re-read (its chapter's `lastModifiedUtc` later than when the snapshot was taken), `export` restores the progress where Kavita lost it (a new volume or a new name gives the chapter new ids): unread stays unread, fully read is marked read, else the pages read are written (shifted by an added or dropped cover page, at least 1, at most the new page count), only when higher than what Kavita holds, or when Kavita still holds exactly the snapshot's page (a same-name file keeps its progress unshifted). A library scan keeps a re-read chapter's old cover image, so once a file whose cover changed is re-read and its progress restored, `export` asks Kavita to regenerate its series' cover images (a forced metadata refresh of the series, 1 per series per run; the series' locked cover stays); a request that fails is logged and asked again by the next run, and no new rewrite of the file is made meanwhile. A rewrite not re-read in time is charged as a chapter waiting on `kavita_scan` is; at the attempt limit its row records the error (`rewrite retry` starts the wait again, `rewrite drop` gives the progress up; its cover refresh stays due, and holds the file until it runs). A restore that fails is logged and tried again by the next run.

A better copy of a published file (SPEC "Library copies") replaces it the same way. It is a download chapter naming the file, and the file's 1 open chapter (the comparison leaves the file alone meanwhile); it goes through junk and convert as any download, named from the file as it is now (its number, title, volume and kind; not resolved, so it changes no other chapter's name or side number; an untitled main file takes its platform list or MangaDex title as a new chapter does, an untitled side file "Side Story <n>") and given the name the pipeline gives a file, in the file's folder (SPEC "Publishing"); a name another file holds, on disk or as its queued rewrite, makes it `needs_human`, as it makes a new chapter at publish. It takes the volume cover the file holds when it is the file's own volume's (the series' stored image of that volume, else the old file's own cover page, stored under `<paths.covers>/volume/` like a fetched one); a file holding another volume's cover, or a cover page that cannot be read, gives none. Publish queues it on the file's row as a rewrite's, with the values publish records for a new file (its source, source name, identity, measurements and date), puts its download aside the retention way and records it as a handled chapter `published`; the chapter ends there. The row's last step takes the copy's values. The progress is the snapshot's pages read scaled to the new page count; Kavita is asked to regenerate the series' cover images. A copy counts as an open rewrite in `export.rewrites_open`, unless its file is an adopted one, when it counts with the conversions and rebuilds (SPEC "State"). An adopted file's conversion is replaced the same way. A replace by a download chapter (a better copy or a conversion) records on the file's row, as its last step, the file's original (where its download went, as at publish: SPEC "Publishing") and where the replaced file was kept (its previous version); a replace given up records neither, and a rewrite of `ComicInfo.xml` or the cover changes neither. A joined file (SPEC "Split chapters") has no original: its pages come from several downloads. `chapter drop` of a held copy removes its staged file, puts its download aside and records it handled `dropped`. A copy's queued replacement given up (`rewrite drop`, or its staged file gone) leaves the file as it is and turns the copy's handled record into `dropped`; its download stays in retention.

A pipeline file can be rebuilt from its original (SPEC "Publishing"): `rewrite rebuild FILE_ID…` gives each named file of origin `pipeline` a rebuild (a converted adopted file is one too, and is converted again from its adopted original). A rebuild is a download chapter naming the file, as an adopted file's conversion is. Its download is a hard link to the file's original, named as that download was, `<paths.staging>/adopted/<published file id>/<source name><suffix>`, so discover parses the identity of the file's first publish. It takes the file's source, and the chapter URL and Suwayomi chapter of the file's newest download chapter of that source (done, not dropped, of its series, whose download had the file's source name); with none (after a `state reset`) its `ComicInfo.xml` `Web` lacks the chapter URL. It goes through every stage as a conversion does, under today's decisions, rules and calibration, and replaces the file the same way. A file is not queued, and is listed with why, when it is unknown or named twice; not of origin `pipeline`, or not confirmed; a joined file; of a series not `ok` or out of scope; without a recorded original or source name, or with its original no longer in retention; when its identity parsed as discover will parse it (its source name, with its original's ComicInfo `Number`) differs from the file's; or busy with a change ("busy"), its rebuild open included ("queued"). The original is read first, outside any transaction; each file is then checked again and queued in its own transaction; the command exits 1 when any file is listed. A chapter whose original is gone by discover, or whose file records none, is `needs_human`: a rebuild never links the published file; `chapter drop` ends it. A rebuild is queued whatever the cap, and counts with the conversions toward it (SPEC "State"). Its download is put aside the retention way, which restarts the original's retention period. A rebuild whose download validate replaces with a new download is a better copy from then on.

A file's previous version can be put back: `rewrite restore FILE_ID…` restores each named file to the version a download chapter's replace (a conversion, a better copy, a rebuild) left in retention as its previous version, under its name then and with the row that described it then. It is queued whatever `export.rewrites_open` (as a rebuild is) and finished by the next `export` as that replace was, with the reader's progress carried; the version it undoes becomes the file's previous version, so naming the file again swaps them back. A volume cover refresh that marks the files holding an old image `stale:V` marks a previous version's recorded cover state too, so a restored file is re-covered. A file is not queued, and is listed with why, when it is unknown or named twice; not confirmed; busy (`rewrite.BUSY`); without a previous version recorded with its row (replaced before restores were recorded); with its previous version no longer in retention, or not a readable archive; with its library file missing; when Kavita refuses its series (read once per series; the other files go on); changed since that replace by a rewrite, a join or `series rename` (its series name, title, volume, cover volume or join differ from what the replace wrote); when its previous name is taken by another file; or of a series not `ok`, out of scope, or not in Kavita. The command exits 1 when any file is listed, 2 at `export.retention_days` 0 (the undone version would not be kept), and stops with Kavita unreachable. A restored adopted file is not converted again until a person acts; `status` counts restored adopted files.

The rewritten files are indexed by the run's 1 library scan. A published file keeps its published-file row throughout (confirmed), so the library-copy check still sees it, under its queued name too. The bulk converter's record is read, never written.

`naming diff [SERIES]` is read-only: per series, the rewrites the comparison would make (file, old and new volume, new name, its cover: inserted, dropped, wanted, or unknown for a file whose cover is not known yet, which it does not read), and apart the differences it does not apply.

A changed title at the sources is reported (log, `status`, Discord; SPEC "Needs human") as a name waiting for `series rename` (Series names, below). The title watched is AniList's English title, less ` @COMIC` (the one a new series is named by): it is changed when the record a check stores holds another, non-empty one than the stored record of the same AniList id, for a series Kavita holds or that is admitted (a new series not yet admitted is named from its record when it is). Each change (old to new) is reported once; `status` lists those of the last 30 days.

### Series names

A series' name is, in order: the `name` of its naming override file; the name a person gave at admission (`series new --name`); AniList's English title, less ` @COMIC` (in any case); else the series' Kavita name, then its localized name, that MangaDex's English alternative titles, else MangaBaka's English titles, else MangaDex's main English title list, hold, that no romanized title (MangaDex `ja-ro`, `ko-ro`, `zh-ro`; MangaBaka's `-ro` titles and romanized title) is, and that is not AniList's romaji title; else its `ComicInfo.xml` name as it is. A name equal to the `ComicInfo.xml` name under Kavita's normalising is that name: another spelling is no change, unless a person gave it (then their spelling is the name). A new series before admission has no `ComicInfo.xml` name: the rule names it, else the names it arrived under. Its romanized name is AniList's romaji title, less ` @COMIC`, else the Kavita name, localized or original name a romanized title is; none when it equals the name under Kavita's normalising.

A name or romanized name is free for a series when no other series of the library, no new series not yet in Kavita and no other series of the same run holds it as any name, under Kavita's normalising; a folder name is free when no other folder in the parent folder has it ignoring case or under Kavita's normalising (the series' own folder aside). Admission and `series rename` use this 1 test. A romanized name that is not free is left out (logged), and the series has none.

A series' names are due when its `ComicInfo.xml` name or Kavita name differs from the rule's name under Kavita's normalising, its Kavita localized name differs from its romanized name (when it has one), or its folder's last part is not the name made safe. This applies to a series with status `ok` that Kavita holds, with a folder, a completed check, and a baseline or admitted as new. A series without a romanized name keeps the localized name it has, unless `series rename` changes its name (then it is emptied).

`series names [SERIES_ID…]` lists, read only and without a lock, what `series rename` would do to each due series and what would stop it; its database reads come from 1 snapshot, ended before any file, override file or Kavita read. `status` lists the series whose names are due from the stored names, a romanized name tested against the stored names of every series of the library (no Kavita or file read; an override file it cannot read, or the share, is a line of the list).

`series rename (SERIES_ID… | --all) [--wait MINUTES]` renames each due series that holds no claimed chapter, no chapter at publish or confirm not done, and no file with a rewrite or copy queued, a wait for Kavita, a cover refresh due or a failed rewrite; an open conversion or rewrite chapter before publish does not stop it (its `ComicInfo.xml` is built at the comicinfo stage from the renamed series). It runs on the machine whose share holds the retention folder on the library's filesystem (the LXC), holds the idle lock exclusive (SPEC "Run lock"): no part runs meanwhile; it refuses to run (exit 2) when `export.retention_days` is 0. It logs each series' Kavita name, localized name, sort name and folder before changing them.

First, for every series of the run: its folder is found (the stored one; after a stop, the target when the stored one is gone and the target holds every published name); the name must be free, the folder name free, and every file's `ComicInfo.xml` must read and rebuild (with the elements the ComicInfo schema takes) and carry as `Series` the stored `ComicInfo.xml` name or the new name; when files are rewritten, the folder must hold no archive Kavita reads (CBZ, CBR, CB7, CBT, ZIP, RAR, 7Z, in any case) the series has no row for (it would keep the old name). A name another series holds makes the series `needs_human`, naming why. Any other failure lists the series and leaves it as it is.

Then, series by series; every Kavita write reads the series just before, resends it whole with only the names and their locks changed (its sort name as read), and reads back the names and locks it sent. A write changing the localized name sets it first, alone, then the name: Kavita refuses to drop a name a folder of the series' files carries unless its stored localized or original name holds it.

1. When files are to be rewritten: Kavita's name becomes the name and its localized name the stored `ComicInfo.xml` name, both locked, so a library scan meanwhile matches every file, old or rewritten, to the 1 series.
2. Every file whose `Series` is not the name is rewritten with `Series` the name and `LocalizedSeries` the romanized name (none: removed); only `ComicInfo.xml` changes; the old file is kept the retention way.
3. The folder is renamed to the name made safe, in its parent folder; denied by the share, it is tried once more 10 seconds later.
4. Kavita's name becomes the name (when it changes; else it stays as Kavita has it) and its localized name the romanized name (empty when none and the name changed), both locked. When no file is rewritten, this write comes first, before the folder rename, so the folder never moves under a name Kavita lacks. When files were rewritten and the folder moved, it waits until Kavita follows the folder (below): until then Kavita lists the files in the old folder and refuses to drop the old name, which stays the localized name; the stored localized and `ComicInfo.xml` names stay the old name meanwhile, so the series is still due and a run that stops first is finished by the next.
5. 1 transaction stores the series' name, `ComicInfo.xml` name, localized name and folder, each file row's path, `ComicInfo.xml` name and recorded size, and the open chapters' `ComicInfo.xml` name.

Each act is done only when due: a series whose only fault is its folder gets steps 3 and 5; one whose only fault is Kavita's name or localized name gets steps 4 and 5. A Kavita write that is refused, fails or does not read back ends that series' rename (listed) and the run goes on; its names stay due, so the next run finishes it. A renamed series that its new names put out of scope (`series.only` named it only by an old name) is listed: that setting must name it anew. Last, when it changed anything, it requests 1 library scan (also when a share error ends the run) and waits until Kavita lists every series whose folder moved in its new folder, requesting again every 10 minutes (a request made while a scan runs does not work), up to `--wait` minutes (default 60); Kavita not answering ends the wait. Each such series that Kavita follows then gets step 4 and its localized name is stored. It exits 1 listing those Kavita has not followed, those a Kavita write refused, and those it left or held. Run again, a rename that stopped part way is finished to the same name. The rules key, junk state and override file stay the series' own.

### Split chapters

A run is the confirmed published files of a series numbered N.1 … N.k (k at least 2, every number from .1 to .k, main chapters, 1 season and 1 volume), all of origin `pipeline`, when no other published file (confirmed or not) is numbered N; a file numbered N that a join made counts as its parts N.1 … N.m. A decimal part written with a leading 0 (N.01) is no part; a number with 2 readings (N.10) never reaches the library (SPEC "Bad downloads"). Beside 2 or 3 parts a file N.5 is an extra chapter, not a part, and the run stands; any other number beyond .k leaves the numbers as they are, as do 2 files of 1 part. A series whose override file says `join_parts: false` has no runs. An adopted part joins once its conversion is done (its file is then of origin `pipeline`); a bulk file never joins. Every part is first published alone, as any chapter is.

Each `export`, after the comparison and under the same cap (`export.rewrites_open`), gives a join chapter to every run of a series that is `ok`, in scope and has a Kavita id, while none of its files is busy (a rewrite, copy or join open or queued on it, a wait for Kavita, a cover refresh due, a failed rewrite), and while no download of the series that is not done is at discover or has the key of N or of one of the run's parts. A series whose override file cannot be read gets none (logged). The join chapter is a rewrite naming the run's first file and listing the others; it starts at comicinfo, which copies the files' pages byte for byte in run order into 1 file in staging, numbered anew from 1 (a leading cover page of the first file keeps its name; a volume cover page of a later file is left out), and writes its `ComicInfo.xml`: the first file's own fields with the series-level fields now (as a rewrite's), `Number` N, `Title` the first title of the run, else "Chapter N", the page count, and every file's `Page` entries in order, re-indexed, a left-out cover's removed (none when a file has none). A file gone, unreadable or holding no page holds the join for a person. Its publish queues it on the first file's row as a rewrite's, under the name of chapter N as a pipeline file is named, once Kavita lists every file of the run; the progress carried is the pages of the parts read in full from the first, plus the pages read in the first part not read in full, over the run's pages. Finish replaces the first file as a rewrite does, then puts each other file in retention and removes it (each repeated safely by a later run). The first file's row then becomes chapter N, in 1 transaction: its identity's number and its `ComicInfo.xml` number N; its page count, junk, strip length and page hashes the files' sums (none when a file has none), its median width the smallest, its bits per pixel the page-weighted mean; how many parts it holds; the chapters naming the other files name it, and their rows are removed. A first join leaves the file no hand-edit record (the joined chapter has none of its own); a join onto a joined file keeps it. A better copy of N replacing a joined file holds no parts.

A new download (no published file named) of part N.j, main chapter, of a series one of whose published files numbered N holds j or more parts, is in the library (its path or its queued one) and is the same chapter by volume (SPEC "Library copies"), is put aside the retention way, recorded handled `duplicate` and dropped ("held in the joined file …"): at discover, and at junk's start for one that was past discover when its join finished. A whole N arriving beside un-joined parts, and a part arriving beside a whole N, are judged as today and published beside them; a whole N in flight when a join publishes leaves the join `needs_human` (its name taken). A joined file is never split again.

### Hand edits

A person corrects a series' chapter titles and volumes with `series edit FILE [--series-id ID]`. FILE is JSON: `{"series": "<Kavita name>", "chapters": {"<chapter>": {"title": "…", "volume": 7}}}`. `series` is matched exactly against the in-scope series' names; it must match 1 (2 series of 1 name: `--series-id` picks one). A chapter is named as a person sees it: `10` (a main chapter without a season), `S2 10` (season 2's chapter 10), `side 3` (Side Story 3); it must name exactly 1 published file or open chapter of the series, as the series' chapters are named now. A field is `title` (a non-empty text; for a side story the text after `Side Story <n>: `) or `volume` (a whole number from 0); `null` removes that field's edit. The whole file is checked before anything is written; every problem is printed and the command exits 2: not JSON, an unknown key or field, no or 2 matching series, a chapter that does not parse or names no chapter or more than 1, a field set on an adopted file (it is not rewritten until it is converted; a `null` is accepted), a side story that is open and not named yet (its side number can still change; a `null` is accepted), a value of the wrong kind, and edits that would give 2 of the series' files 1 file name or 1 volume and number, or make main volumes decrease along the chapter numbers of a season. An entry that is already stored prints `unchanged`. An edit stored before its series was adopted that names a chapter an adopted file holds is kept: the resolver applies it to that file's row, so its neighbours are named by the edited volume, while the file keeps its own name, volume and title until it is converted. The edits are stored in 1 transaction (kept by `state reset`) and printed; nothing is rewritten by the command.

An edit wins over every source, for open chapters and published files alike, and enters the series' naming inputs, so the next `export` compares the series. An open chapter is named with it (its volume, then everything that follows from the volume: the volumes around it, its volume cover, side-story volumes); an edited volume is covered as an override file's is (SPEC "Volume covers"), and in a `season markers` series it ends its season as a recorded season volume does. A published file whose title or volume differs from its edit is rewritten to it as above (renamed when it is a pipeline file; the reading progress carried); a better copy of an edited file keeps the edit. An edit stored after an open chapter was named reaches its file by such a rewrite once it is published. Each file edited keeps the values its sources gave the edited fields (a title as the pipeline recorded it: a bulk-converted file's from its record, untitled as `Chapter <number>`); removing a field's edit rewrites the file back to them, and from there the rules above apply. `naming diff` lists the edits and leaves edited files out of the differences it reports. Kavita (v0.9.1.4) may keep a renamed file's old title when its title goes back to `Chapter <number>`; the file holds the right one.
