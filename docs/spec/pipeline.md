# manga_pipeline spec — Parts, state and chapter stages

Part of the spec; the index is [`SPEC.md`](../../SPEC.md). Update this file in the same change as the behaviour it describes.

## Parts

The pipeline is 3 commands, each working the chapters at its own stages. The database is the hand-off between them: a chapter belongs to 1 part at a time, by its stage, and a part claims it before working on it. No part calls another, and nothing sits above them.

| Part | Work | Talks to |
|---|---|---|
| `intake` | resolves `suwayomi_download`, `bulk_conversion` and `metadata_check` waits; discovers new CBZ files and identifies their series (SPEC "Series identification"); runs metadata checks; takes a series' baseline; queues adopted files' conversions; validates | Suwayomi, the metadata sources, Kavita (read only, for a series the database has not seen) |
| `process` | resolves `junk_decision` and `open_copy` waits; junk; convert | the share only |
| `export` | resolves `kavita_scan` waits; comicinfo; publish; retroactive updates; confirm; 1 library scan; Kavita API writes; empties the retention folder | Kavita, the share |

On the LXC a systemd timer starts each part, and `junk review`, every 10 minutes, at staggered minutes; another starts `watch` every hour (SPEC "Needs human"). `process` also runs on Windows machines (each from a scheduled task every 10 minutes) against the same database; `intake`, `export` and `junk review` run on the LXC only. Parts run at the same time as each other. `intake`, `export` and `junk review` never run twice at once anywhere, and `process` at most once per machine (SPEC "Run lock"); a part with nothing to do exits 0 at once. `process` runs at low CPU and disk priority. Every machine runs the same program with the same shared settings (SPEC "Config"), so a chapter comes out the same whichever machine works it. The timers and the scheduled tasks start each command with `--scheduled`. While the automation is paused (`state pause`), a run started with `--scheduled` exits 0 at once, before its preflight, its schema steps and its log file, printing that the automation is paused and since when; a command run without it works as usual. The pause is a row of the database, so 1 command on any machine pauses every machine. The pause's row and `--scheduled` keep their meaning in every later version, so a deploy that changes the program is paused by the old program and the new alike.

Order of work:

- `intake`, per series: a new series gets its full metadata retrieval; a metadata check runs if one is due (SPEC "Metadata checks"); then the discovered chapters are validated, picked by priority as `process` and `export` pick them. Series due a check that have no new chapters come last.
- Every part picks by priority: a chapter that replaces an adopted file (its conversion, or a better copy that took it; SPEC "State") or rebuilds a file (SPEC "Retroactive updates") after every other chapter; then chapters of series Kavita already knows (it holds their id) before chapters of new series; then the oldest first. They pick again after every chapter, so a new chapter of an ongoing series never waits behind a long new series, and they run until nothing is ready.
- `process` scans every ready junk-stage chapter of a series before it decides any of them, and runs the junk stage for all of them before it converts any, so what repeats across chapters is seen before a decision is made. A chapter that replaces an adopted file, or a rebuild, holds back only other such chapters this way: a download is decided and converted without waiting for its series' conversions and rebuilds to be scanned.
- A part does not claim a chapter of a series in which any chapter is claimed at that part's stages, nor of a series sharing that series' rules key (SPEC "Junk decisions"): machines running `process` work different series at the same time. Between 2 chapters a machine holds no claim, so a series' next chapter may go to another machine; what carries over between a series' chapters (calibration, scans, sightings) is in the database.
- A Windows machine does not claim a chapter whose series folder or download path (for a rewrite, its published file's path) holds a name Windows cannot use over the share (one with `<`, `>`, `:`, `"`, `|`, `?`, `*`, or ending in a dot or a space): a Linux machine works it.
- `export` works in this order each run: it deletes expired retention files, compares the series whose naming inputs changed (SPEC "Retroactive updates"), adds `ComicInfo.xml` to the ready chapters, publishes series by series and finishes the rewrites that queued, then does what needs Kavita: ends `kavita_scan` waits, confirms, publishes the new series that are ready, restores the progress of re-read rewrites, writes series fields when no scan is awaited, then requests at most 1 library scan (SPEC "Publishing"). A chapter of a new series Kavita does not list yet waits on `kavita_scan` at confirm.

Every part works only the series in scope: a series Kavita holds in the library `kavita.library_id`, or a new series (Kavita does not hold it yet); with `series.only` set, only the series it names (by the series' name, its Kavita localized or original name, the `ComicInfo.xml` `Series` a hand-placed folder carries, or the name a new series was admitted under). Nothing else is read or written, except that a part frees the claims a run of it that died left, whatever their series (SPEC "State").

Hand-off between parts:

- `intake` stores what validation measured (page sizes and hashes) in the database. `process` reuses it, and reads the CBZ from the downloads folder itself.
- `process` works on a chapter in a scratch folder on local disk and deletes it when the chapter leaves `process`, so local disk holds only the chapters in hand. It writes the finished chapter as a CBZ of pages into the staging folder on the share. `export` adds the `ComicInfo.xml` to that file and renames it into the library; the pages are packed once. Finished chapters therefore wait on the share, not on the machine's disk.
- A chapter waiting on a junk decision keeps no scratch folder: its stored scan and its candidates' images, in the candidates folder (`paths.candidates`, on the share), are all it needs until they are decided.
- Covers `intake` fetches go to `paths.covers`, on the share, where `process` on any machine reads them.
- A part works only on chapters that are ready for its own stages; a chapter waiting on another part is not its concern.

One chapter that fails or waits never stops a part or the chapters after it. Later chapters of the series are published while an earlier one is held.

When Suwayomi, Kavita, a metadata source or the share cannot be reached, the chapters and series that need it wait and are tried again by a later run of the part. That does not count as an attempt. For the rest of the run the part claims no chapter at the stage that met the unreachable service, and goes on with its other stages. For the share, "cannot be reached" is an input/output, stale-handle or timeout error raised while a part works on files, a disk with no space left, or on Windows a network error (a network name or path no longer available, a network that does not respond) or a full disk; the program does not tell which disk raised it, and logs the error's text.

## State

One PostgreSQL 17 database on a server (on the LXC), reached with the settings of SPEC "Config", from every machine that runs the pipeline. The run locks are locks of the database (SPEC "Run lock"), so they hold across machines. Any machine may run the commands without a lock (`status`, `retry`, `chapter use`, `chapter drop`, `series link`, `junk list`, `junk show`, `junk decide`, `junk rows`, `junk row`, `junk redecide`, `junk undo`, `rewrite rebuild`) against the same database. It holds 3 kinds of data:

| Kind | What |
|---|---|
| workflow state | every chapter with its stage, what it waits on, its attempts and its last error; each series' status |
| knowledge | the junk decisions and each series' watermarks; each series' source IDs and conversion calibration |
| sync records | what was fetched for each series, from which source and when (written only by `intake`, with a version that rises on every change); what was written for each series and each published chapter (written only by `export`, with the version it was written from) |

It is the single record of what is pending. `state reset` clears the workflow state only; knowledge and sync records are kept, and the next `intake` rediscovers the downloads (what becomes of a re-download in progress: SPEC "Bad downloads"). Every series becomes ok again, except one held for want of a Kavita series or a folder: only `series link` (or `series new`, for a new series not yet admitted) settles that. It needs `--yes`, runs only while no part and no junk review is running on any machine, and also empties the staging folder (but the staged files of queued rewrites: SPEC "Retroactive updates"), the candidates folder (after moving the images decisions keep into its `decided` folder, which it keeps) and the scratch folder of the machine it runs on. Queued rewrites and their progress snapshots are kept (they are on the published files' rows), and every series is compared again. The Discord queue is kept (SPEC "Needs human"). It never touches the downloads, the library or the retention folder.

A part claims a chapter in 1 short transaction before working on it and records the outcome in another; no transaction is open while a stage works. A claim names its owner (`process@<host name>` for `process`, else the part's name) and a count that rises with every claim of the chapter: an outcome, and every claim check, compares both, so a run never passes for a later run of the same owner. A claim is freed when its owner's session (the database connection holding its run lock) has ended: a part's start frees its own owner's claims, and every claim transaction frees those of any other owner of its part whose session has ended. A machine that died, or slept until the server ended its session, so has its claims freed within the next claim another machine makes; a woken machine's next statement fails and its run ends. With `lock.enabled` false no session holds a lock, and no claim is freed. A command without a lock refuses a chapter a part has claimed, except `series link`: a chapter it moves to another series from past the junk stage goes back to junk with its claim freed, and the part's outcome for it is dropped. An outcome is not recorded over a change a person made meanwhile.

A run whose claim was freed meanwhile (it slept, or its connection dropped) records no outcome and spends no attempt. Before each act it cannot undo outside the database (putting a download aside, writing or replacing a junk candidate's images, moving or rewriting a staged file), a stage confirms on the database that it still holds the claim, and every write it makes before its outcome that records this chapter's work (calibration samples, a kept notice's note) checks the claim in its own transaction. A series value filled once by whichever chapter reaches it first (the layout) is written without the check: an empty value is filled and a filled one is never replaced, whoever writes. The page aspect is computed again at each page-layout chapter's junk scan and read and written in 1 transaction, without the check, unless it is the record's: the series stores where its page aspect came from (`record`, the baseline's from the record, never replaced; `computed`, the junk scan's) apart from where its layout came from, which an override file changes. Its staged file and scratch folder carry the claim's count in their names, so 2 claims of 1 chapter never share a file.

Every time the program stores comes from the database server's clock, so no 2 machines' clocks are ever compared over a stored time. The clean-ups of day-old files (staged files and `.part` files no chapter names, candidate folders no row names) compare a file's time with the machine's own clock; a day's margin makes a skew harmless.

A stored path is its root's name and the path below that root, with `/` separators (`library/<series>/<file>.cbz`; roots `downloads`, `library`, `staging`, `retention`, `candidates`, `covers`); each machine maps it to and from its own path by its configured root (SPEC "Config"), so Linux and Windows machines share the rows. 2 columns are not stored paths: a junk candidate's folder and a volume cover's file each hold a name relative to their 1 folder (`paths.candidates`, `paths.covers`), with no root in front. A series folder Kavita reports outside `paths.library` makes the series `needs_human` with the folder named (`series link` refuses it); any other path to be stored that lies under no root is an error naming the path, never stored as it is. A database holding paths in another form (absolute paths an older version stored) is refused when the program first opens it, naming what to do: build a new database.

Every write transaction runs alone: it takes 1 database-wide lock first, so no 2 write transactions overlap, whichever run they come from; a transaction is milliseconds long. `status` reads everything it prints from 1 snapshot, so its counts agree while parts run. A connection lost mid-run ends the run as an unexpected error (exit 1); its claims are freed as for a run that died.

The database's structure is built by ordered schema steps, each recorded once applied; 2 runs opening a database at once apply each step once. A database holding a step the program does not know is refused, and nothing ever recreates a database by itself. A database is built (created on the server when missing, as UTF-8 with bytewise text order, and its steps applied) only by `state adopt` and `junk restore`; a part, `junk review`, `state reset` and `state version` never create or build one: finding none, or one that holds no schema record, they exit 4 before taking a lock (SPEC "CLI"). For every other command too, a database that does not exist or holds no schema record is no database: `status` says so, and `retry`, `chapter use`, `chapter drop`, `series link`, `junk list`, `junk show`, `junk decide`, `junk rows`, `junk row`, `junk redecide`, `junk undo` and `junk backup` refuse with exit 2, building nothing.

A series Kavita already holds gets a baseline before anything is published into it: the first time its bulk-converter record (`.optimizer.json` in the series folder) parses, the record's chapters are recorded as published files (origin `bulk`, confirmed), its CBZ sources as handled chapters (fate chapter, merged, carried or failed as published; duplicate or replaced as duplicate; deleted as dropped; each with its `pages_digest`), its layout as the series' layout, the record's page aspect (when it has one) as the series' page aspect, marked as the record's, its calibration's probed groups as the series' fixed qualities (SPEC "Calibration"), and the junk decisions it carries (SPEC "Junk decisions"), in 1 transaction. No library file is opened for a record series. A record that exists but does not parse (partial, broken, without a `strip` or `pages` layout, or with malformed junk decision rows) makes the series `needs_human`, naming what is wrong: a person fixes or removes the record, then `retry --series`. A series with no baseline and no stored folder takes its folder from Kavita first (stored), so a record in it is the series' baseline. A series whose folder holds no record and that has no baseline is adopted once it has completed a metadata check and none of its chapters is at discover; until then its chapters wait on `bulk_conversion`. Adoption reads the series' `.cbz` files as Kavita lists them, every one in the series' single folder, each file no published file holds yet read as a download is: its identity and number from its name and `ComicInfo.xml` `Number` (the name first), its volume its own (`Vol.N` in its name, else its `ComicInfo.xml` `Volume`; volume source `filename`), its title as a download's, its kind from its side label, its source name its file stem, its page count from its pages (a `000_cover` page left out), its volume cover from its member list (a page `000_cover`, as for any file the pipeline did not record a cover for); a `ComicInfo.xml` that cannot be read gives no fields, and the name gives what it can. The series' layout is its override file's `layout` when it names one, else measured over the content pages of its first, middle and last files (by number), as a new series' is measured over its chapters. Its volume basis is chosen as a new series' is, over its published files, those files and its open chapters. Then it records in 1 transaction: the files as published files (origin `library`, confirmed), the layout (unless the series has one), the basis (unless the series has one), and the series' `ComicInfo.xml` name: the `Series` its files carry (the value most of its files carry, by exact text; a tie: the one equal to Kavita's original name, else the first by sort; values that differ under Kavita's name normalising make the series `needs_human`, naming them; a name that is none of the series' Kavita names under that normalising, likewise; no file carrying one: Kavita's name). Each adopted file's recorded `ComicInfo.xml` series is its own `Series`, else the series' name. No calibration, junk decision or handled chapter is recorded: its conversions calibrate its groups from samples and Claude decides its junk. A series records nothing and is `needs_human`, naming what is wrong (a person fixes it, rescans the library in Kavita, then `retry --series`), when: Kavita gives it no single folder, or no file; a file Kavita lists lies outside that folder; a file is missing or cannot be opened, has no pages, no number, or a number with 2 readings (26.10); a file is other than `.cbz`; 2 files are 1 chapter (the same season, side label and number, and volumes that do not differ where both come from the files, as Library copies compares them: a side story has no volume of its own, so its key alone tells it apart); a sampled file's pages cannot be decoded; or its override file cannot be read. A missing file is the share's problem (the run's), not the series', while the share is not mounted (its folders or its owner file missing, as the share checks of SPEC "Preflight" find them). A Kavita error reply leaves the chapter waiting, tried again by a later run. A series once adopted is never baselined again from a record that appears later. A series whose bulk files were recorded without their source name, kind and volume source (an older baseline) has them filled from the record at its next chapter's validate; with its record gone, or one that does not parse, the series is `needs_human` likewise. A new series has no record: its layout is the `layout` its override file names (SPEC "Publishing"), else is measured once over up to 3 of its chapters (first, middle and last to arrive) among those past validate whose download this machine can read; its first chapter waits at junk until 3 such chapters exist or none of its chapters is left at discover or validate. An override file's `layout` (`strip` or `pages`; anything else makes the chapter `needs_human`) is any series' layout from its next chapter at junk; when that changes the series' layout, its downloads at junk are scanned again under it (a `needs_human` one once it is retried) and those at convert go back to junk, while a chapter already converted is published as converted. The baseline also fixes the series' `ComicInfo.xml` names (SPEC "Publishing"); a record whose series name is not one of the series' Kavita names records nothing and makes the series `needs_human`.

A published file of origin `library` is an adopted file not yet converted: its download as it was, recorded as published. Each goes through the pipeline as a download does and replaces itself (its conversion).

At each run, `intake` gives a download chapter naming it to each adopted file that is confirmed, in an `ok` series in scope, and named by no chapter. It works in order of series and number, while fewer than `export.rewrites_open` chapters that replace an adopted file, and rebuilds (a chapter whose download is a link under `<paths.staging>/adopted/`), are open (those held `needs_human` count); at 0 it queues none.

The chapter's download is a hard link to the library file, `<paths.staging>/adopted/<published file id>/<file name>`. It takes no space, and every act that removes a download moves the link, never the library file. Discover makes the link before it reads the download. It keeps a link that is its file, removes any other file at the path unread (anything that is not a file is a link error), and links. A file that is missing or cannot be linked, while the share is mounted, makes the chapter `needs_human`, naming the file; `retry` makes it ready at discover, which links it again. Validate gives the chapter the volume cover its file holds. At its start, the queue removes the link folders that no open chapter's download is in.

A conversion goes through every stage as a better copy of its file (SPEC "Retroactive updates"):
- discover, where it is never put aside as a handled chapter, since its pages are already published;
- validate, where a bad file is downloaded again as a hand-placed download is, and the new download takes its place;
- junk, where it is not judged as a notice, and Claude decides what the series' stored decisions do not;
- convert, comicinfo and publish: named from its file (SPEC "Retroactive updates"), with the volume cover its file holds.

It is queued on the file's row and finished by `export`, and the old file is kept the retention way. The file then has origin `pipeline` and the measurements and junk that publish records.

A file whose chapter ended without replacing it (dropped by a person, or its queued replacement given up) and that is not busy with a change is left as it is; only `state reset` queues it again. `status` counts the adopted files not converted and the conversions open (and, when any is open, the rebuilds open, those waiting at junk and those `needs_human`), and lists each file left as it is, with its chapter and why: the chapter's drop reason, or "replacement given up" for a chapter that ended at publish without being dropped. `state reset` removes the links with the staging folder, and the next `intake` queues the conversions again.

1 database owns the share at a time: a file in the staging folder holds the owning database's id, written by `state adopt --yes`. A part or `junk review` that finds the file missing (the share is not mounted, or was never adopted) or holding another id stops before any work (SPEC "Preflight").

The database holds the fleet's version: 1 digest over the program's files, the shared settings (SPEC "Config"), the installed versions of the runtime dependencies and each image tool's and the scorer's version, set by `state version --yes` once per deploy or change of a shared setting. A part or `junk review` whose own digest differs, or that finds none stored, stops before any work (SPEC "Preflight"), so every machine that works runs the same program with the same settings and libraries.

## Chapter stages

A chapter is at 1 stage and has 1 status: `ready`, `claimed`, `waiting`, `needs_human` or `done`. A stage ends done, waiting (with what it waits on) or failed; or it leaves the chapter ready to be claimed again in the same run (the junk stage after a scan); or it drops the chapter (the chapter is `done` where it stands, never published), or makes it `needs_human` at once when no further attempt can change the result. A chapter that failed is tried again by a later run of its part, never in the same run, and no machine claims it for 5 minutes after the failure (by the database's clock); its series' other chapters go on meanwhile. Anything else that makes the chapter ready (`retry`, `chapter use`, a move by `series link`, any other outcome) ends that pause. A chapter that reaches its attempt limit (`workflow.attempt_limit`) becomes `needs_human` and is left alone until a person acts. The check that ends a wait can also make the chapter `needs_human` (a junk candidate Claude was unsure of, or one past the review limit). A series can be `needs_human` too (for example when its source IDs disagree); its chapters wait until a person clears it.

| Stage | Part | Does | Can wait on |
|---|---|---|---|
| discover | `intake` | settles the chapter's identity, its number and its content digest (an archive it cannot read gets no digest and goes on to validate; a `ComicInfo.xml` that cannot be read or does not parse gives no number); drops a download already handled, an unnumbered notice or hiatus page (SPEC "Bad downloads") and a part a joined file holds (SPEC "Retroactive updates", Split chapters); a chapter with no number, or a number with 2 readings (26.10), is `needs_human` | |
| validate | `intake` | drops a download renamed away (SPEC "Bad downloads"); then first takes the series' baseline (SPEC "State") and holds a chapter whose series has never completed a metadata check (its name and volume cover need the data), or, on a platform volume basis, whose arrival's check has not completed (SPEC "Metadata"); reads and measures every page; a bad download is re-downloaded, and its replacement validated here; other defects are `needs_human` or noted (SPEC "Bad downloads", "Validation") | `bulk_conversion`, `metadata_check`, `suwayomi_download` |
| junk | `process` | drops a download already handled, or one renamed away (SPEC "Bad downloads"); waits while another open copy of its chapter is ahead of it (SPEC "Library copies"); drops a duplicate of a published file, or holds a better or doubtful copy (SPEC "Bad downloads", "Library copies"); judges a numbered notice title once: kept with a note, or dropped (SPEC "Validation"); scans the chapter's junk units, applies the stored decisions and writes the chapter edit convert applies (SPEC "Junk decisions") | `junk_decision`, `open_copy` |
| convert | `process` | re-encodes the pages (AVIF where it passes the quality gates) and writes the CBZ of pages to the staging folder; for a rewrite, copies the library file's pages and inserts or drops its volume cover (SPEC "Retroactive updates") | |
| comicinfo | `export` | adds `ComicInfo.xml` to the CBZ (SPEC "Metadata", ComicInfo) | |
| publish | `export` | renames the CBZ into the series folder | |
| confirm | `export` | checks Kavita indexed the file, then removes the download (a rewrite has none) | `kavita_scan` |

The CBZ in the downloads folder is never modified. Work happens in the scratch folder.

## Conversion

The convert stage re-encodes a chapter as the bulk converter does: the same tools with the same arguments, the same route and the same gates, so a chapter it converts matches what the bulk converter writes for it. It writes nothing in the series folder (`.optimizer.json` included).

- Input: the download's pages, measured once (page format, chroma, colour class: the stored page rows where they exist), the chapter's junk edits (`chapter_edit`), and its volume cover when it takes one (`volume_cover`). Pages are taken under the bulk converter's names: `001`, `002`, … (at least 3 digits) in reading order with their format's extension; a cover-named page keeps its name, or gets the number of the pages before it in front when its own name would sort out of place. A chapter with no edit row, or one whose keys or value types are wrong, is a program error: `needs_human` at once. So is an edit that drops every page. So is a page whose EXIF orientation is a rotation or mirror (2–8), and a chapter whose taken names would share a stem or would not sort in reading order both naturally and plainly (a cover-named page inside the chapter). A stored measurement that is not the page's (another sha1) fails the chapter.
- Layout (`series_conversion`): a strip chapter is stacked at its most common page width, the junk edits' removed rows are taken out, and the rest is cut into pages of 1500–5000 px on its gaps. A page chapter drops the edits' pages, crops their bands, then joins sliced pages and, when the edit says the chapter is split, cuts it: with `split_pages` n, its stack into n equal pages (cuts crossing its images); otherwise each image into its whole number of pages at the series' page aspect. Cover-named pages are never reshaped: they stay single pages ahead of the rendered ones. With no page aspect stored for the series, a split takes the page height its images imply, as the bulk converter does. A page-layout series' page aspect, unless it came from the series' record (whatever the layout's origin: an override file names a layout, not an aspect), is computed at each junk scan from the measured pages (page rows) of the series' live chapters (open, or published and not dropped by a person): each page whose height over width is at least 0.9 and below the stitched ratio counts, and the 3 most common shapes (to 3 decimals) held by at least 3 pages are kept, most common first. It replaces the stored one when the 2 differ to 2 decimals; when no page counts, the stored one stays (with none stored, the chapter's own are taken). A chapter whose series has no layout stored fails.
- Logo blanks (the edit's `blank`: a page, a box in that page's own pixels, a fill colour): each box is filled with its colour on the source page before any other edit, and only in an AVIF outcome and in a rendered chapter's lossless outcome; any other lossless or untouched outcome keeps the logo (a gray-mark page is still stored gray there). A blanked page is encoded from its blanked pixels and scored against them; the size gate counts its source bytes. A blank on a dropped or cover-named page, a second blank on 1 page, a box outside its page or a fill that is not 1 RGB colour is a program error: `needs_human` at once.
- Route, per chapter, never per page, from the kept pages' formats. JPEG, PNG and lossless WebP only: AVIF, else lossless. With lossy WebP among them: AVIF, else untouched. Only lossy WebP, GIF, AVIF: untouched. Any other mix: untouched. A rendered chapter (strip, split, crop or join, or a kept page in JPEG XL): AVIF, else its rendered pages lossless, so its junk stays removed and no page is in a format Kavita cannot show (it reads PNG, JPEG, WebP, GIF and AVIF pages only). A chapter that is not rendered, takes a volume cover whose AVIF passed, and whose non-cover pages are of more than 1 format or of one with no cover encoding: AVIF under the floor only, else untouched.
- AVIF: gray, tinted and gray-mark pages encode at 4:0:0, scored against their gray version; colour pages keep the source's chroma (a JPEG XL page's counts as 4:4:4). Each page encodes at its group's quality (gray or colour; SPEC "Calibration") with `avifenc -s 6 -j 1`; a colour JPEG avifenc reads as Pillow does (RGB, sRGB or no profile, no EXIF rotation) is fed to it directly, every other page as a PNG of its pixels. The AVIF is decoded with `avifdec` and scored with SSIMULACRA2 on the GPU (Vship). A page under 80 is encoded once more at q90. The AVIF stands when every page scores ≥ 80 and, for a chapter that is neither rendered nor taken to AVIF for its volume cover (Route: floor only), the AVIF pages total ≤ 0.90 × the source pages' bytes; the first page that fails stops it.
- Lossless: JPEG through `jpegtran -optimize -progressive` (gray and gray-mark YCbCr or 1-component JPEGs with `-grayscale`), PNG through `oxipng -o 4 --strip safe` (gray and gray-mark pages made gray first), lossless WebP copied. Every page's pixels are verified; a page whose output is not smaller keeps its source bytes. A rendered chapter's lossless pages are its rendered PNGs (blanked where the edit blanks) through `oxipng`, a gray page made gray first when its own pixels also show no colour (a crop moves the colour tiles), any other page left colour (a rendered page's class is its source pages'), each verified against its rendered PNG; the size rule does not apply to them, and a volume cover goes in as PNG.
- Volume cover (`volume_cover`: a file under `paths.covers`, by a path relative to it, and its sha256): it goes in as the page `000_cover`, in place of a page of that name, scaled down (never up) to the most common width of the download's non-cover pages (of all its pages when it has none; the first seen wins a tie). Its AVIF is encoded at q80 (q90 retry) and scored before the route is chosen, at its own class and chroma. An AVIF outcome takes the cover as that AVIF encode, when it scored ≥ 80; a lossless or untouched outcome takes it in the 1 format the chapter's non-cover pages share: AVIF (that encode), JPEG (quality 92), PNG or lossy WebP (quality 90); none when the pages share no such format or the AVIF cover is needed and failed, and the chapter then goes out without it, with the reason logged and recorded. A path that is absolute or leads outside `paths.covers`, a missing file or another sha256 fails the attempt; convert never deletes the file. The cover, and the page it replaces, do not count for whether every page is gray.
- Output: a store-mode CBZ of the pages in reading order, at `<paths.staging>/<database id, first 8 characters>-<chapter id>-<claim count>.cbz`. At its start `process` deletes a staged `.cbz` that no chapter names, and a `.cbz.part` a killed write left, once it is a day old (a run whose claim was freed may have left one); nothing else in the staging folder is touched. Pages keep their taken name's stem with their new extension; rendered pages are numbered `001`, `002`, … after the cover-named pages.
- Post-check, on the staged file: store mode, no folders or extra entries, every page decodable, in a format Kavita reads (PNG, JPEG, WebP, GIF, AVIF), with an extension matching its format, page count and order (sha1s) as encoded, lossless pages pixel-equal to their sources, every AVIF page scored ≥ 80 (the cover by its own encode), and for the lossless (but a rendered chapter's) and size-gated AVIF outcomes the output pages' bytes not above the source pages' (an inserted cover's bytes are left out). A failed check deletes the staged file and fails the chapter.
- Result, on the chapter: the staged file and its size; the route, outcome, quality per group, scores, pages in and out, dropped pages, reshape, the blanked pages, the inserted cover or why one was not, and whether every page is gray (`convert_result`); the output pages with their width, height and bytes (`output_pages`). Convert's notes, in the chapter's notes (each starting `convert:`; a later convert of the chapter replaces them and keeps the others): an AVIF rejected, why, and what was published instead; an encode group whose AVIF pages' mean score is below 83 at a calibrated quality under 80 (`quality-drift`); a split's irregular images (not within the snap window of a whole number of pages); a re-sliced chapter and its page count; the staged file under 10 % of the download's bytes; the `untouched-flag` route and its formats; colour JPEG pages of an AVIF outcome whose chroma subsampling is not 4:4:4, 4:2:2 or 4:2:0 (encoded as 4:4:4); a lossless chapter (not rendered) whose pages stay in more than 1 format; animated pages encoded as 1 frame for a volume cover; and, on the chapter whose samples fix a calibration group, the group, its quality, why and its samples' chapters. A page an inserted volume cover replaced counts in no note.
- The chapter's scratch folder (`<paths.scratch>/<chapter id>-<claim count>/`, on the machine's local disk) holds every work file and is removed when the stage ends, whatever the outcome. At its start `process` removes the chapter folders a killed run of it left in its own `paths.scratch` and nothing else there (not with `lock.enabled` false, when another run may be using them).
- Pages are rendered with Pillow. `pyvips` was measured on 5 sample chapters (2026-11-13: 206 rendered pages): 0–2× faster and up to 30 MiB more memory, pixel-identical except where a page is resized to the strip width (2 pages, max difference 166 of 255); not adopted, since a rendered page must match the bulk converter's.
- Pages are encoded and decoded by `convert.workers` processes, started fresh (never forked) per chapter; scoring runs on 3 threads of the `process` command, which holds the GPU.

## Calibration

The AVIF quality is per series and encode group: gray (pages encoded 4:0:0) and colour (the rest). A group is fixed or open.

- Fixed from the series' bulk-converter record at the baseline: each group the record probed (its `probes` list is not empty) takes the record's quality, whatever scorer the record was made with. A group the record left unprobed (no page of the group, or too few sample pages, so it stayed at q80), or lacks, is open.
- Fixed from a spread of an adopted series' files by the calibration spread (`scripts/calibrate_spread.py`), run once before the adopted files' conversions with no part running, as the bulk converter calibrated: for each adopted series in scope, `ok`, holding no group fixed this way, its adopted files (origin `library`) are taken in number order; those with an AVIF page, as convert would plan them, are usable (every strip file is); 3 are picked spread over them (first, middle and last); each is planned as convert plans it with no junk edit (a strip file rendered; a page file split as junk would split it (stitched or re-sliced), and rendered), and its AVIF pages are its units (the rendered pages when it renders; cover-named pages, and rendered pages made from one, left out). Per group, 40 units are shared among the 3 files, the file with fewest units first, evenly spaced in each; a page whose bytes or rendered image repeat is probed once and its scores counted for each. With 20 or more, the fix rule below applies to their scores; with fewer, none included, the group is fixed at q80. A group a record fixed is never changed. Each group fixed this way records why with `spread:` and the 3 files, and no samples. A page series with no stored page aspect takes it from its files' measured pages for the stitched test. A file that cannot be read, decoded, planned or rendered, and a picked one that gives no unit, is left out and named, and the 3 are picked again over the rest; the share failing, or an encode error, leaves the series' groups as they were. A series adopted later calibrates from its conversions.
- The quality settings (q80, the q90 retry, speed 6, the floor 80, the size ratio 0.90, the ladder, 14 and 40 sample pages, 20 samples, 20 counted samples, the mean 85) are fixed values of the program, not settings.
- An open group encodes at q80. Each chapter whose first outcome is AVIF adds samples to a group once only (a retried chapter or a second run adds none): up to 14 of its pages of that group (cover-named pages, and rendered pages made from one, are never samples), and none once the group holds 40 (evenly spaced, the rendered pages for a rendered chapter; a page whose bytes or rendered image were sampled before is passed over), each encoded at q80 and at 75, 70, 65, 60, 55 and 50 and scored. Samples are knowledge: `state reset` keeps them.
- The group is fixed once it holds 20 samples, from any number of chapters (the bulk converter's rule). Its quality is the bulk converter's choice from the stored scores: going down the ladder from 75, each step counts the samples that score ≥ 80 at q80 and fails with fewer than 20 of them (so 20 samples with fewer counted fix the group at q80), a mean below 85 or a minimum below 80; the quality is the last step before the first failure, else 80. The chapter that fixes the group already encodes at the fixed quality; chapters converted earlier are not re-encoded.

## Needs human

A chapter or a series that becomes `needs_human` is reported 3 ways: a line in the log (`needs human: <kind> <id>: <reason>`), the `status` command, and a message to a Discord webhook (`notify.discord_webhook`). A series title changed at the sources is reported the same 3 ways (SPEC "Retroactive updates").

The Discord message is queued with the change, in its transaction, by whichever command makes it; `export` sends what is queued at the end of every run, a run that ended early included, and `watch` sends it every hour. A report is queued once per kind, item and text (the text names the item, its series, a chapter's identity and stage, and the reason), so the same series, or the same chapter, becoming `needs_human` again for the same reason (after `retry`, or for a series after `state reset`) sends nothing new; a new reason is a new message. A chapter made after `state reset` is a new item. A message is plain text: what, which series and chapter, the reason, then ` -> ` and the command that clears it, as `status` shows it; it holds at most 2000 characters (UTF-16 code units), the reason cut so the command stays whole, mentions ping no one, and links show no preview. Incidents (below) are sent first, 1 message each, never in a digest. More than 5 other unsent reports go as 1 digest message: their count, the first 5 (oldest first, each cut to its share), and "The rest: `status`". Each report is claimed before its post, so 2 senders never post 1 twice; a crash between the claim and the post loses that 1 message (the log and `status` still have it). Discord unreachable, or refusing the webhook (HTTP 401, 403, 404, or 500 and above): the report stays queued for a later run, the send stops, and the run goes on with its result unchanged. Any other refusal (Discord refuses the message itself) marks that report refused; it is never sent, `status` lists it, and the send goes on. With no webhook set, Discord is off: reports stay queued and `status` counts them.

3 incidents are reported in the log and by 1 Discord message each, queued and sent as a report is (kind `incident`, with a fix):

- a part with no successful run in 24 hours: `intake`, `export`, `junk review`, and `process` per machine, each by the last success its run records hold (SPEC "Parts"). Only a run whose result is `ok` succeeds, so a run that ended unreachable or with an error, one refused by its lock, its preflight or a missing database, and one killed before its end all leave the last success where it was. A part that has never recorded a success is not watched;
- downloads not taken (`status`'s downloads not taken) 24 hours after they were first seen: 1 incident per folder, named by its oldest such download;
- Kavita refusing the API key (SPEC "Services"), queued at the end of an `intake` run that met it.

A stall's or a folder's message names the time its incident started (the part's last success, the folder's oldest first sighting), so it is sent once while it lasts, and again only after it has cleared and started anew. The key's message is 1 fixed text, queued once while the refusal lasts and sent at least once; an `intake` run whose library listing Kavita answers removes it once sent, so the next refusal is a new message. Nothing is sent when an incident clears. `watch` finds the first 2 every hour and sends what is queued; it needs only the database and a webhook (it refuses to run without one), so it reports a part that stops at its preflight, a timer that stopped and `export` itself. Nothing reports the LXC, its database or `watch`'s own timer being down, nor a config or schema every command refuses; every deploy ends with a run of `watch` by hand.

A person clears it with `retry` (a chapter by its id, or `--series` for a series and its chapters): the item is ready again at the stage where it stopped, with its attempts at 0. With no database, an id that does not exist, or an item that is not `needs_human` (a chapter a part has claimed included), is refused with exit code 2 and left unchanged; `--series` is refused when neither the series nor any of its chapters is `needs_human`, and for a new series not yet admitted (SPEC "Series identification"). A chapter held at validate can also be settled with `chapter use`, one held at discover, validate or junk with `chapter drop`, and `retry` there starts a re-download's source search again (SPEC "Bad downloads").
